# Brickadia gate study — 5 November 2026

Reviewed all **396 registered definitions** in the pinned `brs-js@4.0.4` library: brick variants, input/output ports, saved-field types and available defaults. The same version was current on npm and the upstream master package manifest during this review. The inventory contains 349 `BrickComponentType_*` definitions and 47 `Component_*` definitions; that is not 396 freestanding logic gates. Seventeen have no canonical standalone brick asset in this registry. Several types share a saved struct (330 distinct structs).

The exhaustive per-definition reference is [gate-reference/GATES.md](gate-reference/GATES.md). Its [JSON companion](gate-reference/gates.json) includes defaults and directly referenced enum values. Recreate both with `node tools/prefabs/catalogue-gates.cjs`; the generator checks complete registry/schema/port coverage and rejects unclassified definitions. This is a review of exposed interfaces, not 396 runtime experiments. Gates added to an installed game newer than these definitions could be absent. The official wiki could not be fetched through this environment's network policy; no claims below depend on reading it.

## What the available interfaces establish

| Family | Available operations / relevant distinctions |
| --- | --- |
| Functions and chips | Function Definition supplies a `Definition` output; Function Call accepts that reference plus Exec and eight indexed inputs, exposes eight indexed outputs, Completed, bAborted and IterationsExecuted. Function Input/Output carry labels, order and default values. Callable entry gates expose Body execution. Ordinary microchips have separate Microchip Input/Output ports. |
| Loops | Count For has Count, FirstIndex, Step and an entry Index. For Each Array has Index/Value; For Each Map has Index/Key/Value. Loop chip structs have bRunAcrossTicks (default false), bRunning, completion/abort and iteration counts. Those interfaces make bounded work within a tick plausible; they do not establish what every body gate supports. |
| Abort handling | The enum distinguishes invalid plan/collection, overflow, collection modified, recursion, work limit and nesting limit. Exact limits and behavior must be tested. A map/array loop should not be assumed safe to mutate its iterated collection. |
| Variables | A Var exposes VarRef/Value. Explicit Get, Set and Increment operate on VarRef. Set has bChangeType. Explicit Get gives an execution path for reads, but its output publication timing must still be checked. |
| Arrays | Twenty-four operations plus ArrayVar: get/set, find, length, append/copy, fill/resize/slice, insert/remove/push/pop, reverse/shuffle/swap, join, reductions and sort. Sort Multiple has up to eight array references plus success status; verify alignment/ties/mismatched lengths before depending on it. |
| Maps | MapVar plus get/set/has/remove/clear/copy, keys/values and length. Get has bFound. Get Keys has bIncludeDead, relevant to weak-object keys. A map reference is distinct from an individual key's result. |
| Change detection | Value-change detector, execution-triggered change detector and Container Change Detector. Edge Detector has pulse outputs; Edge Detector Exec has execution outputs. Initial seeding is saved state and needs a first-trigger check. |
| Time and motion | Clock, Stopwatch, Buffer Seconds/Ticks, Queue Seconds/Ticks, Dampen, Tween, delta time, uptime, epoch/date. Buffers carry Input/Output and saved Buffered state; queues carry eight data channels and saved Entries. They are different mechanisms. Tween has Arrived; Dampen has smoothing velocity. Blend is an expression with an alpha, not automatically a timed animation. |
| Flow and events | Branch, Union, Toggle, Cycle, random, local/global custom events with up to eight data channels, command and gamemode events, loaded/whole-grid events. Object-event flags and Target are distinct from including a player/entity in event data. |
| Math and logic | Arithmetic, clamp/remap/blend/easing, rounding, trigonometry, logs, comparisons, selection/swap, boolean and bitwise logic. Numeric/enum conversion has separate gates. WireValue inputs do not prove which cross-type operations/coercions are supported. |
| Strings | Format with seven named inputs, concatenation, split/search/replace, trim/case, substring/length, parse integer/number and Unicode conversion. Check success/found outputs. String Split occurrence 1 is confirmed by this project's in-game fixes; occurrence 0 previously broke catalogue parsing. |
| Spatial math | Vectors, distances and squared distances, normalize/scale/cross/dot, direction↔rotation, quaternion operations and rotation/vector splitting. Rotator and quaternion are different saved types. The present model simplifies some conversions and does not validate the engine's complete coercion rules. |
| Colors | Linear/sRGB construction/splitting, hex, color-space conversion and blending. Stored byte Color and LinearColor are distinct. Text decal color is a TextDisplay property, separate from a brick's color. |
| Players and characters | User ID/name/display name, entity/controller/character lookup, input and aim queries, damage/ammo/inventory, permissions/roles/trust, respawn and private messages/dialogues/HUD text. Aim gives Origin/Direction and a bLocalAim setting; it should not be confused with a raycast hit location. |
| Game data | Individual/team leaderboard get/set/increment, team lookup/assignment/pinning, array population from players/team members, rounds and winners. These are the numeric stat interfaces used by the shops. They expose no atomic multi-stat transaction. |
| Entities | World transforms, velocities and speed, visibility/per-player visibility, freeze/gravity, tags/teams, custom properties/copy/remove, teleports and destruction. Destroy Spawned and Destroy Spawned Prefab are separate operations. Get Own Transform is placement-sensitive; its exact context in a chip must not be assumed equivalent to a gate outside it. |
| Zones | Attached Zone supplies ZoneRef, occupation state/count and filtering. Entity/character/projectile enter/leave and brick-change/remove events are separate types. Zone Get Players/Entities fill array references. Reconciliation can query actual occupants instead of relying only on event history. |
| Collision queries | Sweep and Simple Sweep expose Hit/Miss, hit location/normal/entity/brick/color/distance. The general sweep has world/relative mode, filters and ignored entities; the simple variant has fewer wireable inputs and more saved-only settings. |
| Prefabs and other spawning | Exec Prefab Spawner has explicit Exec/ExecOut, Entity, DestroyAll, limit/lifetime/offset/rotation/velocity. Prefab Spawn has bSpawnEnable/RespawnTime/SpawnedEntity. Other families spawn bots/items/projectiles/explosions. These interfaces do not prove when a spawned object's internal graph is ready. |
| Component/property access | Brick and component references, get/set brick/component/environment properties, get/add/remove component, grid read and own transform. Saved configuration selectors are not always wire ports. Runtime graph-changing operations deserve isolation because this project has hit a graph-execution assertion. |
| Interaction/UI/audio | Buttons/animated buttons, switches, touch/pressure plate, targets, TextDisplay, lights, audio emitters and one-shot/client/global/positioned audio. Button bHeld is a held state: use an edge for one action per press. Display `VisibleTo`, enabled state, geometry colliders and entity visibility are separate controls. |
| Vehicles/physical mechanics | Seats, wheel engines/joints/suspension, aero surfaces, gyroscopes, thrusters, bearing/slider/motor/servo/rigid variants, sockets and mass. WheelEngine has manual controls, discovery, force/handling/steering, mass distribution and flight settings; these are not just decorative bricks. |
| Asset references | Eleven reference definitions cover bricks/entities/items/pickups/projectiles/fonts/audio/particles/resources/engine audio. A canonical brick is absent for some references; that is not permission to invent an asset path. |

## Consequences for the loadboard

The loadboard currently uses deliberate buffers, queued parallel arrays and a 0.1-second polling pump. The eight-channel server inbox drains/saves fields in sequence with additional waits, and many leaderboard/query writes are buffered too. That adds avoidable latency even without a large gate count.

Functions could hold request arguments as call-local inputs and return assembled responses; native loop chips could replace repeated graph branches or manual per-tick iteration. Explicit reads and completion paths might remove some waits. These are optimization candidates, not an instruction to remove all buffering. The test should establish output publication, body execution, abort behavior and whether a function's Completed path is safe to consume immediately.

For UI browsing, another candidate is displaying an already-received catalogue locally while keeping the authority responsible for acceptance, ownership and payment. That can improve perceived scrolling latency independently of Functions, but stale-revision checks must remain. No loadboard changes are made as part of this study.

## What a saved test prefab can answer

A small manual test can retain expected inputs, immediate and delayed results, body/completion counters and elapsed timer values in ordinary Var gates and display them as text. Reading that exported save lets us compare results without relying on a screenshot. It cannot recover every historical wire pulse unless the test explicitly records it. Stopwatch resolution and real network/rendering latency are separate from same-graph execution ordering.

One working Function example would also establish native chip assembly conventions if generated definition/call wiring is rejected. There is no need for a prefab containing every gate. Definitions do not have to have appeared in an uploaded prefab for their metadata to be available.
